# RAG 为什么不只使用向量数据库

## 结论

RAG 可以只使用向量数据库，但在工程文档、代码知识库、配置手册、错误日志、API 参数等场景中，更稳妥的做法通常是同时使用 FTS 和向量召回。

向量召回负责理解语义相似，FTS 负责精确命中关键字符串。两者覆盖的问题不同，不是简单的替代关系。

## 向量召回擅长什么

向量召回适合处理自然语言问题和语义相近的表达。

例如用户问：

```text
怎么配置本地知识库？
```

即使文档里没有完全一样的句子，向量召回也可能找到包含以下内容的片段：

```text
RAG 配置
corpusRoots
ingest
rag.json
```

这种能力来自 embedding 模型对语义相似度的建模。它适合解决“用户用自己的话提问，但资料里是另一种说法”的问题。

## FTS 擅长什么

FTS 适合处理精确字符串匹配，尤其是工程系统里常见的不可改写信息。

典型例子包括：

- 环境变量：`AI2NAO_RAG_DB`
- 配置文件：`rag.config.example.local-llm.json`
- 模型名：`text-embedding-3-small`
- 命令参数：`--rag-db`
- 函数名：`defaultRagDbPath`
- 错误码、异常信息、日志片段
- 文件路径、类名、接口名、数据库字段名

这些字符串的价值往往就在于“字面完全相同”。向量模型可能知道它们大致属于配置、代码或参数，但不一定会把它们排在最前面。

对于工程类 RAG，很多答案不是抽象语义，而是某个精确名称、路径、参数或错误文本。此时 FTS 的召回稳定性很重要。

## 只用向量数据库的问题

只用向量召回时，常见风险包括：

1. 精确词丢失  
   用户输入一个环境变量、文件名或报错片段时，向量检索可能认为其他语义相近的段落更相关。

2. 专有名词排序不稳  
   embedding 模型对项目内部命名、缩写、局部约定的理解通常不如对自然语言稳定。

3. 代码和配置片段语义稀薄  
   代码符号、参数列表、JSON 字段等内容不一定有充分自然语言上下文，向量相似度容易波动。

4. 排查问题时可解释性较弱  
   FTS 命中可以清楚说明“因为这个词出现了”，而向量命中更多依赖模型相似度。

## 双路召回的价值

双路召回一般指同时运行两条检索链路：

```text
用户问题
  -> FTS 召回
  -> 向量召回
  -> 融合排序
  -> 返回证据
```

它的价值在于：

- FTS 兜住精确名称、路径、参数、错误信息
- 向量召回补足同义表达、泛化问题、自然语言问题
- 融合排序让两类证据共同竞争，减少单一路径失误

例如用户问：

```text
serve 启动时 RAG 数据库路径怎么指定？
```

向量召回可能找到“RAG 配置说明”“本地索引机制”等语义相近内容。

FTS 则很可能稳定命中：

```text
--rag-db
AI2NAO_RAG_DB
defaultRagDbPath
```

最终融合结果既能包含语义相关说明，也能保留精确参数。

## 为什么常用 RRF 融合

RRF，即 Reciprocal Rank Fusion，是一种常见的多路召回融合方法。

它不强依赖不同召回器的分数尺度一致，而是主要利用各自排序名次：

```text
score = 1 / (k + rank_fts) + 1 / (k + rank_vector)
```

这样可以避免直接比较 FTS 的 BM25 分数和向量相似度分数。因为这两类分数不是同一种量纲，直接相加通常不可靠。

RRF 的特点是简单、稳定、容易调试，适合作为双路召回的首版融合策略。

## 什么时候可以只用向量

以下场景可以考虑只使用向量数据库：

- 语料主要是自然语言文章、FAQ、知识库说明
- 用户问题很少包含代码符号、路径、参数、ID、错误日志
- 业务可以接受少量精确词召回损失
- embedding 模型质量足够高
- 有额外 reranker 或人工反馈机制补偿排序问题

例如客服 FAQ、产品帮助中心、通用知识问答，向量召回通常可以承担更多职责。

## 什么时候应该保留 FTS

以下场景建议保留 FTS：

- 面向开发者文档、代码库、配置手册
- 语料里有大量 API 名称、文件名、函数名、参数名
- 用户经常粘贴错误日志、命令、路径或精确标识符
- 答案需要引用精确字段或配置项
- 系统需要较强的可解释性和稳定兜底

在这些场景下，FTS 不是落后方案，而是关键能力。

## 推荐实践

对于工程类 RAG，推荐采用：

```text
FTS + 向量召回 + RRF 融合 + 调试页面 + 黄金集评测
```

其中：

- FTS 保证精确命中能力
- 向量召回提升语义泛化能力
- RRF 负责融合排序
- 调试页面用于观察三路结果
- 黄金集评测用于长期验证检索质量

这个组合通常比单独使用向量数据库更稳，也比单独使用 FTS 更懂自然语言。

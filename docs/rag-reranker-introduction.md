# RAG Reranker 技术介绍

## 什么是 Reranker

Reranker 是 RAG 系统中的二次排序器。

它通常不负责从全量语料中直接搜索文档，而是在召回器已经找出一批候选结果后，对这些候选结果重新打分、重新排序。

典型流程如下：

```text
用户问题
  -> 召回器检索候选文档
  -> Reranker 判断每个候选与问题的相关性
  -> 重新排序
  -> 选择 TopK 片段交给大模型生成答案
```

简单来说：

- 召回器负责“先找出可能相关的一批内容”
- Reranker 负责“从这批内容里挑出真正最相关的内容”

## 为什么需要 Reranker

第一阶段召回通常追求覆盖率，也就是宁可多捞一些可能相关的内容，也不要漏掉正确答案。

但召回结果的排序不一定足够精准。常见问题包括：

- 语义相近但答案不在其中
- 命中了关键词但上下文不相关
- 多个片段都相似，但只有其中一个真正回答问题
- 排名前几条看起来相关，实际不适合喂给大模型

Reranker 的作用就是在候选池里做更细粒度的相关性判断。

## Reranker 和向量检索的区别

向量检索通常使用 bi-encoder 架构。

它会分别把问题和文档编码成向量，然后通过向量距离或相似度进行检索。

```text
query -> embedding
doc   -> embedding
similarity(query_embedding, doc_embedding)
```

这种方式速度快，适合大规模召回，因为文档向量可以提前计算并存入向量数据库。

Reranker 通常使用 cross-encoder 或类似机制。

它会把问题和候选片段放在一起，让模型直接判断二者是否相关：

```text
input:  问题 + 候选片段
output: 相关性分数
```

这种方式更准，但更慢，因为每个候选都需要单独计算。

## 典型架构

常见 RAG 架构中，Reranker 位于召回之后、生成之前：

```text
用户问题
  -> FTS 召回
  -> 向量召回
  -> 候选合并
  -> Reranker 重排
  -> TopK 上下文
  -> LLM 生成答案
```

候选池通常会比最终上下文大。

例如：

```text
召回阶段取 Top50
Reranker 重排 Top50
最终选择 Top5 给 LLM
```

这样可以让召回阶段保留足够覆盖率，同时让最终上下文更精准。

## 常见 Reranker 类型

### Cross-Encoder Reranker

Cross-encoder 会把问题和文档片段作为一组输入，让模型输出相关性分数。

优点：

- 排序质量通常较高
- 能理解问题和文档之间的细粒度关系
- 对歧义问题和相似片段更敏感

缺点：

- 计算成本较高
- 延迟比向量检索更大
- 不适合直接对全量文档运行

### LLM-as-Reranker

LLM-as-reranker 使用通用大模型对候选片段进行排序或打分。

它可以让模型判断：

```text
这个片段是否能回答用户问题？
```

或让模型输出候选排序。

优点：

- 容易接入
- 判断能力强
- 可以根据业务规则做复杂排序

缺点：

- 成本和延迟较高
- 输出需要约束和解析
- 批量处理时吞吐较低
- 结果稳定性需要评测验证

### Lightweight Reranker

轻量 reranker 可能使用较小模型、规则特征或传统排序模型。

例如结合以下特征：

- BM25 分数
- 向量相似度
- 文档新鲜度
- 标题命中
- 路径权重
- 用户权限或业务优先级

这种方式不一定比专用模型更准，但成本低、速度快、可解释性强。

## Reranker 的输入与输出

Reranker 的输入通常包括：

- 用户问题
- 候选片段文本
- 候选片段标题
- 文件路径或来源
- 召回阶段分数
- 召回来源，例如 FTS 或向量召回

输出通常是：

- 相关性分数
- 排序后的候选列表
- 是否相关的二分类判断
- 可选的相关性解释

最常见的是输出一个数值分数，然后按分数从高到低排序。

## Reranker 解决什么问题

Reranker 主要解决“召回到了，但排序不够准”的问题。

例如用户问：

```text
如何配置数据库连接超时时间？
```

召回阶段可能返回：

```text
1. 数据库连接配置总览
2. 数据库连接池参数
3. API 超时时间配置
4. 数据库连接超时 retry 机制
5. 日志配置
```

其中多个片段都含有“数据库”“连接”“超时”等词，但真正回答问题的可能是第 2 条。

Reranker 会逐条判断候选与问题之间的直接相关性，把最能回答问题的内容排到前面。

## Reranker 的代价

Reranker 不是免费能力。引入它需要考虑以下成本。

### 延迟

如果候选池有 50 条，reranker 可能需要对 50 个“问题 + 片段”组合进行计算。

即使可以批量处理，也会比单纯向量检索慢。

### 成本

如果使用云端模型或大模型 rerank，每次检索都会增加 token 或推理成本。

候选池越大，成本越高。

### 复杂度

系统需要新增：

- reranker 模型配置
- 批处理逻辑
- 超时和降级策略
- 评测指标
- 调试工具

### 稳定性

Reranker 可能改善排序，也可能在某些问题上把正确结果降权。

因此上线前需要用固定评测集验证，而不是只凭主观感觉判断。

## 什么时候应该引入 Reranker

适合引入 reranker 的情况：

- 第一阶段召回能找到答案，但正确片段经常不在前几名
- 语料中有大量相似文档或重复片段
- 用户问题复杂，需要更细粒度的相关性判断
- 最终上下文窗口有限，只能放少量片段
- 回答质量高度依赖引用证据的准确性
- 已有评测集，可以量化 reranker 是否提升效果

## 什么时候可以先不用 Reranker

可以暂缓引入 reranker 的情况：

- 语料规模较小
- TopK 结果已经足够准确
- 系统对延迟非常敏感
- 不希望增加额外模型依赖
- 没有评测集，无法判断 reranker 是否带来真实收益
- 当前主要问题是召回不到，而不是排序不准

如果问题是“正确内容完全没被召回”，reranker 通常帮不上忙。它只能重排已有候选，不能凭空找回没有进入候选池的文档。

## Reranker 与 RRF 的关系

RRF，即 Reciprocal Rank Fusion，是一种多路召回融合方法。

RRF 主要解决：

```text
如何把 FTS 结果和向量结果合并成一个候选排序
```

Reranker 主要解决：

```text
如何对候选结果做更精准的相关性判断
```

二者可以组合使用：

```text
FTS 召回 + 向量召回
  -> RRF 初步融合
  -> Reranker 二次排序
  -> TopK 上下文
```

也可以在召回合并后直接 rerank：

```text
FTS 召回 + 向量召回
  -> 去重合并
  -> Reranker 排序
  -> TopK 上下文
```

实际选择取决于候选池大小、延迟预算和实现复杂度。

## 评估指标

引入 reranker 后，建议至少观察以下指标：

- Recall@K：正确答案是否出现在前 K 个结果中
- MRR：第一个正确结果排得是否足够靠前
- NDCG：整体排序质量
- Answer Accuracy：最终回答是否正确
- Citation Accuracy：引用的证据是否真的支持答案
- Latency：检索链路耗时
- Cost：每次查询的额外成本

其中 Recall@K 更偏召回能力，MRR 和 NDCG 更偏排序能力。

Reranker 的主要目标通常是提升 MRR、NDCG 和最终引用质量。

## 工程建议

引入 reranker 时，建议遵循以下顺序：

1. 先做好基础召回  
   确保候选池中经常能包含正确答案。

2. 建立黄金评测集  
   准备一组真实问题和期望命中的文档，用于量化排序变化。

3. 从较小候选池开始  
   例如先召回 Top30 或 Top50，再 rerank 到 Top5。

4. 设置超时和降级  
   如果 reranker 超时或失败，应回退到原始融合排序结果。

5. 对比上线前后指标  
   不只看单个案例，要看整体评测集上的平均收益。

6. 控制上下文质量  
   最终给大模型的片段宁可少而准，也不要多而杂。

## 总结

Reranker 是 RAG 中提升排序质量的重要组件。

它不替代 FTS、向量数据库或其他召回器，而是在候选结果已经被召回后，对候选进行更精细的相关性判断。

它适合解决“找到了但排序不准”的问题，不适合解决“根本没有召回到”的问题。

在工程实践中，reranker 通常应该在基础召回稳定、已有评测集、且排序质量成为瓶颈之后再引入。这样可以更清楚地判断它是否真的提升了 RAG 系统的整体质量。

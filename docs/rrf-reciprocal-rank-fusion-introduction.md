# RRF Reciprocal Rank Fusion 技术介绍

## 什么是 RRF

RRF，全称 Reciprocal Rank Fusion，中文通常可以理解为“倒数排名融合”。

它是一种用于合并多个排序结果的算法，常见于信息检索、搜索系统和 RAG 检索系统中。

RRF 的核心思想很简单：

> 如果一个文档在多个检索器里都排得靠前，那么它更可能是高质量结果。

它不直接比较不同检索器返回的原始分数，而是只使用每个结果在各自列表中的排名。

## 为什么需要 RRF

在实际搜索系统中，经常会有多个召回器。

例如：

- BM25 / FTS 关键词检索
- 向量相似度检索
- 标签检索
- 图关系检索
- 时间或热度排序
- 个性化召回

这些召回器返回的分数往往不是同一种量纲。

例如：

```text
BM25: 13.72
Cosine similarity: 0.82
Vector distance: 0.19
Freshness score: 1683921023
```

这些分数不能简单相加，也不能直接比较大小。

RRF 通过使用排名而不是原始分数，绕开了“不同召回器分数不可比”的问题。

## 基本公式

RRF 对每个候选结果计算一个融合分数：

```text
RRF(d) = Σ 1 / (k + rank_i(d))
```

其中：

- `d` 表示某个文档或候选结果
- `i` 表示第 i 个召回器
- `rank_i(d)` 表示文档 `d` 在第 i 个召回器结果中的排名
- 如果某个召回器没有返回文档 `d`，则该召回器对 `d` 的贡献为 0
- `k` 是一个常量，常见取值是 60

最后按 `RRF(d)` 从高到低排序。

## 示例

假设有两个召回器：关键词检索和向量检索。

关键词检索返回：

```text
1. A
2. B
3. C
```

向量检索返回：

```text
1. C
2. D
3. A
```

取 `k = 60`。

则各文档得分为：

```text
A = 1 / (60 + 1) + 1 / (60 + 3)
B = 1 / (60 + 2)
C = 1 / (60 + 3) + 1 / (60 + 1)
D = 1 / (60 + 2)
```

可以看到：

- A 在两路召回中都出现，分别排第 1 和第 3
- C 在两路召回中也都出现，分别排第 3 和第 1
- B 只在关键词检索中出现
- D 只在向量检索中出现

因此 A 和 C 通常会排在 B 和 D 前面。

## k 参数的作用

RRF 中的 `k` 用来控制排名差异对最终分数的影响程度。

当 `k` 较小时，靠前排名的优势更明显。

例如 `k = 10`：

```text
第 1 名贡献：1 / 11
第 10 名贡献：1 / 20
```

当 `k` 较大时，不同排名之间的差异会被平滑。

例如 `k = 60`：

```text
第 1 名贡献：1 / 61
第 10 名贡献：1 / 70
```

很多实践会使用 `k = 60` 作为默认值，因为它比较稳定，不会让单一路召回的第一名过度支配最终排序。

## RRF 的优点

### 不依赖分数校准

RRF 不需要知道 BM25、向量相似度、距离分数、业务分数之间如何换算。

只要每一路召回器能给出排序列表，就可以融合。

### 实现简单

RRF 的实现非常直接：

```text
遍历每个召回列表
记录候选结果排名
累加 1 / (k + rank)
按总分排序
```

不需要训练模型，也不需要复杂参数。

### 对多路召回友好

RRF 天然适合多个召回器。

不仅可以融合两路召回，也可以融合三路、四路甚至更多路召回。

### 稳定性好

因为 RRF 使用排名而不是原始分数，所以对不同检索器分数分布变化不敏感。

这在工程系统中非常有用。

## RRF 的局限

### 不理解内容语义

RRF 只看排名，不会阅读文档内容。

它无法判断一个片段是否真的回答了用户问题。

如果需要更细粒度的相关性判断，通常需要引入 reranker。

### 依赖召回质量

如果所有召回器都没有召回正确结果，RRF 无法凭空生成正确结果。

它只能融合已有候选。

### 对召回器质量一视同仁

基础 RRF 默认每一路召回器权重相同。

如果某一路召回器明显更可靠，可能需要加权 RRF 或其他融合策略。

### 不能处理复杂业务目标

如果排序目标包含权限、商业优先级、新鲜度、多样性、用户画像等复杂因素，单纯 RRF 可能不够。

这时通常需要结合规则、reranker 或 Learning to Rank。

## Weighted RRF

基础 RRF 可以扩展为加权版本：

```text
WeightedRRF(d) = Σ w_i * 1 / (k + rank_i(d))
```

其中 `w_i` 是第 i 个召回器的权重。

例如：

```text
关键词检索权重：1.0
向量检索权重：0.8
标题检索权重：1.5
```

加权 RRF 适合某些召回器明显更可靠，或业务上希望偏向某一路结果的场景。

但权重需要通过评测数据调试，不建议凭感觉随意设置。

## RRF 与 Reranker 的区别

RRF 和 reranker 都会影响最终排序，但它们解决的问题不同。

RRF 解决的是：

```text
如何把多个召回器的排序列表合并起来
```

Reranker 解决的是：

```text
如何判断候选片段和用户问题是否真的相关
```

RRF 不读取候选内容，只使用排名。

Reranker 通常会读取：

```text
用户问题 + 候选片段
```

然后输出相关性分数。

两者可以组合使用：

```text
多路召回
  -> RRF 初步融合
  -> Reranker 二次排序
  -> 最终结果
```

## 适用场景

RRF 适合以下场景：

- 多路召回结果需要融合
- 不同召回器分数不可直接比较
- 希望快速得到稳定的融合排序
- 没有训练数据
- 不希望增加模型调用成本
- 需要简单、可解释、易调试的融合策略

典型应用包括：

- 搜索系统的多通道召回融合
- RAG 中的 FTS + 向量召回融合
- 文档搜索中的标题召回 + 正文召回融合
- 推荐系统中的多个候选源初步融合

## 不适用或不充分的场景

RRF 不适合单独解决以下问题：

- 候选内容需要深度语义判断
- 正确结果没有进入任何召回列表
- 排序目标包含复杂业务收益
- 需要学习用户点击反馈
- 需要强个性化排序
- 需要控制结果多样性

这些场景通常需要结合其他方法。

## 工程实现要点

实现 RRF 时需要注意以下几点。

### 统一候选 ID

不同召回器返回的同一个文档必须能被识别为同一个候选。

例如使用：

- 文档 ID
- chunk ID
- URL
- 数据库主键
- 规范化后的路径

如果无法去重，同一个结果可能会被当成多个候选，影响融合质量。

### 控制候选池大小

每一路召回通常不会无限返回结果。

常见做法是：

```text
每路召回 Top20 到 Top100
融合后取 TopK
```

候选池过小可能漏掉正确答案，候选池过大则会增加后续处理成本。

### 记录来源和排名

为了方便调试，建议保留：

- 候选来自哪些召回器
- 在每一路中的排名
- 每一路贡献的 RRF 分数
- 最终融合排名

这些信息可以帮助判断某个结果为什么排在前面。

### 使用评测集调参

`k` 值、召回 TopN、是否加权，都应该通过评测数据验证。

不要只凭单个查询的主观感觉调整。

## 简单伪代码

```text
function rrf(lists, k = 60):
  scores = {}

  for each list in lists:
    for rank, doc in enumerate(list, start = 1):
      if doc.id not in scores:
        scores[doc.id] = 0
      scores[doc.id] += 1 / (k + rank)

  return docs sorted by scores descending
```

如果使用加权 RRF：

```text
function weighted_rrf(weighted_lists, k = 60):
  scores = {}

  for each (weight, list) in weighted_lists:
    for rank, doc in enumerate(list, start = 1):
      if doc.id not in scores:
        scores[doc.id] = 0
      scores[doc.id] += weight * 1 / (k + rank)

  return docs sorted by scores descending
```

## 总结

RRF 是一种经典、简单、稳健的多路排序融合方法。

它最大的价值是避免不同召回器分数不可比的问题，只依赖各自排名来合并结果。

RRF 很适合作为多路召回系统的默认融合策略，尤其适合在没有训练数据、没有 reranker、希望快速稳定上线的阶段使用。

但 RRF 不是万能排序器。它不理解内容语义，也无法弥补召回缺失。对于更高精度的排序需求，通常需要在 RRF 之后加入 reranker、规则排序或学习排序模型。

# CopilotKit 最佳实践与使用场景

本文总结 CopilotKit 在 ai2nao 这类本机 AI 工作台里的最佳使用方式。重点不是“让 AI 帮用户点按钮”，而是把自然语言意图映射成前端应用中的状态读取、工作流编排、可视化反馈和人工确认。

## 一句话定位

CopilotKit 适合做 **AI 驱动的前端应用操作层**：

- 让 AI 理解当前页面状态、用户选中的对象和业务上下文。
- 让 AI 调用前端已经拥有的操作能力，例如切换会话、打开面板、触发搜索、填写表单。
- 让 AI 的工具调用结果以 React 组件、证据卡片、确认面板或进度状态展示出来。
- 在高风险动作前暂停，等待用户确认。

它不应该被理解成浏览器里的“万能本地 agent”。读写项目文件、执行命令、访问私有数据库、修改源码等动作，应该落在后端 tool 或本地 agent runtime 中，前端只负责展示、确认和交互。

## 最适合的场景

### 1. 跨页面和跨面板的工作流

用户往往不会说“请点击左侧第 3 个会话，再点右侧搜索按钮”。真实表达更像：

```text
帮我找到最近关于 RAG 配置的聊天，并把相关证据打开给我看。
```

这个需求涉及多个 UI 区域：

- 历史会话列表
- 当前选中会话
- RAG 检索
- 证据展示区
- AI 对话区

CopilotKit 的价值在于让 AI 把一句自然语言拆成一组页面动作：读取工作台状态、筛选候选会话、切换到目标会话、调用 RAG 检索、渲染证据卡片，再用文本说明结论。

### 2. 当前页面上下文感知

普通聊天模型不知道用户正在看什么页面、选中了什么对象、当前配置是什么。CopilotKit 可以把这些前端状态暴露给模型：

- 当前页面路径
- 当前会话 ID 和标题
- 选中的仓库、文件、日期或任务
- 当前模型状态
- RAG 是否可用
- 最近操作记录

适合的用户问题：

```text
根据我当前打开的会话，帮我解释这次 RAG 结果为什么不准。
```

```text
我现在这个页面还有哪些信息可以用来判断问题？
```

### 3. 结构化结果展示

纯文本回答不适合展示所有工具结果。CopilotKit 的工具渲染能力适合把模型调用结果显示成业务组件：

- RAG 证据卡
- 文件候选列表
- 会话候选列表
- 任务计划草稿
- 删除确认面板
- 多步骤执行进度

这类 UI 比聊天框里塞 JSON 或长文本更适合真实产品使用。

### 4. Human-in-the-loop

AI 可以提出动作，但危险动作必须让用户确认：

- 删除会话
- 保存计划
- 覆盖已有配置
- 批量修改记录
- 触发长时间任务

推荐模式：

```text
AI 生成动作建议
-> 前端展示确认 UI
-> 用户批准或拒绝
-> 工具继续或中止
```

这比让模型直接执行动作安全，也比完全禁止自动化更有用。

### 5. Agent-native UI

当页面本身不是静态表单，而是一个由 AI 参与驱动的工作台时，CopilotKit 的价值更明显。例如：

- AI 对话工作台
- RAG 调试台
- 开源雷达分析页
- 本地知识库浏览器
- 计划生成与评审工具

这些页面的共同点是：用户目标通常跨越搜索、筛选、阅读、比较、解释和保存，不是单个按钮能完成。

## 不适合的场景

### 1. 只有问答，没有业务状态

如果产品只是：

```text
用户问一句
AI 回一段文本
```

CopilotKit 的价值有限。普通聊天接口、AI SDK 或自定义流式 UI 就能满足。

### 2. 需要本地系统权限的动作

这些动作不应直接放在前端 CopilotKit tool 里：

- 读取 `/Users/...` 下的任意文件
- 创建或修改项目文件
- 执行 shell 命令
- 安装依赖
- 操作 git
- 访问服务端私钥或 `.env`

正确做法是后端提供受控 tool：

```text
ai2nao_read_file
ai2nao_write_file
ai2nao_patch_file
ai2nao_run_command
```

并且增加路径白名单、敏感文件拦截、人工确认和审计记录。

### 3. 为了“炫技”让 AI 点按钮

如果一个动作用户自己点一次更快，就不值得做成 CopilotKit tool。好的 tool 应该满足至少一个条件：

- 它跨多个页面或面板。
- 它需要综合当前上下文。
- 它能减少重复筛选、搜索、对比。
- 它能把复杂结果用结构化 UI 展示出来。
- 它需要在自动化和人工确认之间取得平衡。

## 前端 tool 与后端 tool 的边界

### 前端 tool 适合做

- 读取当前页面状态
- 切换当前 UI 选中项
- 打开弹窗、抽屉或详情面板
- 调用已有 HTTP API
- 展示工具结果组件
- 等待用户确认

示例：

```text
ai2nao_read_workspace_context
ai2nao_select_session
ai2nao_search_rag_evidence
ai2nao_confirm_session_delete
```

### 后端 tool 适合做

- 读写文件
- 查询数据库
- 执行受控命令
- 调用私有服务
- 执行长任务
- 处理敏感数据

推荐数据流：

```text
用户自然语言意图
-> 模型请求 tool call
-> 后端校验参数和权限
-> 后端执行真实动作
-> 前端展示结果和确认 UI
```

## ai2nao 的最佳首批落地案例

### 案例 1：会话与证据导航

用户说：

```text
帮我找到最近关于 tool calling 的聊天，并把相关 RAG 证据列出来。
```

AI 应该：

- 读取当前工作台上下文。
- 根据会话标题和最近消息找候选会话。
- 切换到最相关会话。
- 调用 RAG 证据搜索。
- 渲染证据卡片。
- 说明使用了哪些上下文。

价值：用户不用在会话列表、RAG 搜索和聊天区之间来回切换。

### 案例 2：RAG 结果诊断

用户说：

```text
这次回答为什么没有引用我本地资料？
```

AI 应该：

- 读取 RAG 状态。
- 检查当前会话是否启用了 RAG。
- 查询相关证据。
- 展示命中的证据数量、来源和片段。
- 如果没有命中，解释可能原因：未索引、关键词不匹配、topK 太低、模型未使用证据。

价值：把“模型为什么没用资料”从黑盒变成可观察流程。

### 案例 3：删除或覆盖前的确认

用户说：

```text
把这个测试会话删掉。
```

AI 应该：

- 识别当前选中会话。
- 展示删除确认面板。
- 等用户批准后再调用删除动作。
- 删除后自动选择下一个合理会话。

价值：让 AI 可以参与危险操作，但不会绕过用户确认。

### 案例 4：生成计划并挂到当前上下文

用户说：

```text
把刚才讨论的后端 tool calling 方案整理成实施计划。
```

AI 应该：

- 读取当前会话上下文。
- 生成结构化计划草稿。
- 在计划面板里展示目标、步骤、风险和验收标准。
- 等用户确认后保存。

价值：把聊天内容转成可执行工作流，而不是停留在文本回答。

## 设计原则

### 1. Tool 名称要表达业务动作

推荐：

```text
ai2nao_search_rag_evidence
ai2nao_select_session
ai2nao_confirm_session_delete
```

不推荐：

```text
click_button
run_action
do_thing
```

模型需要理解 tool 的语义，开发者也需要从日志里看懂它做了什么。

### 2. 参数要结构化且保守

tool 参数应该使用明确 schema：

```text
query: string
topK: number
sessionId: string
reason: string
```

避免把一整段自然语言塞进一个 `payload` 里让工具自己猜。

### 3. 前端 tool 不要伪装成系统权限

前端工具的描述要诚实。例如：

```text
读取当前页面已知的工作台状态
```

不要写成：

```text
读取用户本机所有项目状态
```

如果能力需要后端权限，就做后端 tool。

### 4. 工具结果必须可见

用户要知道 AI 做了什么。推荐每个重要 tool 都有可视化结果：

- 调用了哪个工具
- 输入是什么
- 返回了什么
- 是否失败
- 后续动作是否需要确认

这会显著降低“我问了但没看出作用”的困惑。

### 5. 高风险动作默认人工确认

以下动作应该默认 human-in-the-loop：

- 删除
- 覆盖
- 写文件
- 批量更新
- 执行命令
- 调用外部服务产生副作用

### 6. 后端仍然要做权限校验

前端确认不是安全边界。任何真正产生副作用的后端 API 都必须自己校验：

- 参数类型
- 路径范围
- 敏感文件
- 操作白名单
- 请求来源
- 错误输出脱敏

## 推荐架构

```text
React 页面
  -> 注册 CopilotKit context 和 frontend tools
  -> 展示工具结果、确认 UI、进度 UI

/api/copilotkit
  -> 接收消息、上下文和工具定义
  -> 校验 tool 白名单
  -> 把 tools 传给 AI SDK streamText
  -> 持久化 AG-UI 消息

后端 tool API
  -> 执行文件、数据库、命令等真实能力
  -> 做权限校验和审计
  -> 返回结构化结果

模型/provider
  -> 必须支持 tool calling
  -> 不支持时只能退化成普通聊天
```

## 验收标准

一个 CopilotKit 功能可以上线前，至少应该回答清楚：

- 用户真实意图是什么？
- 这个意图是否跨多个 UI 状态或业务对象？
- tool 调用后用户能否看到可理解的结果？
- 失败时是否有明确提示？
- 危险动作是否需要确认？
- 真正的权限动作是否在后端执行？
- 当前模型/provider 是否实际支持 tool calling？

## ai2nao 的下一步建议

### P0：增加工具调用自检

新增一个开发期检查能力，用无害 tool 验证当前模型是否真的会发起 tool call。它应该区分三种失败：

- 前端没有注册 tool。
- 后端没有把 tool 传给模型。
- 当前模型/provider 不支持或没有返回 tool call。

### P1：把 RAG 证据工具做成强可见 UI

当 AI 调用 RAG 搜索时，页面必须显示证据卡片。用户应该能看到：

- 查询词
- 命中数量
- 来源路径
- 分数或排序
- 片段

### P2：增加后端只读文件 tool

可以先做最保守版本：

```text
ai2nao_read_indexed_file
```

只允许读取已经被 ai2nao 索引过的文件，不允许任意路径读取。这样比直接开放 `read_file(path)` 更安全，也更符合 ai2nao 的产品边界。

### P3：增加计划草稿确认流

把聊天内容生成计划草稿，并在保存前由用户确认。这个能力可以验证 CopilotKit 在“聊天转工作流”上的价值。

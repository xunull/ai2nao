# `max-w-[Npx] mx-auto` 是响应式写法:可读内容列 与 分区自适应

> 起因:`/agent-messages` 页两边留白过宽的诊断(2026-07-03)。澄清一个常见误解——
> 「写死 max-width 就不是响应式」是错的;真正的问题在**封顶取值**与**一刀切**,不在技术本身。

## 1. 结论先行

`max-w-[900px] mx-auto` **本身就是响应式布局的一种**:

- **窄屏(视口 < 900px)**:内容**流式撑满**可用宽度(`max-width` 不生效,元素跟着容器缩)。
- **宽屏(视口 ≥ 900px)**:宽度**封顶 900px**,`mx-auto` 把它**水平居中**,两侧留等宽外边距。

这是十几年来「可读内容列(readable content column / measure column)」的标准做法。Bootstrap 的
`.container`、Tailwind 的 `container` / `max-w-*` + `mx-auto`、几乎所有内容站点的正文容器,都是这套。
它响应视口变化,只是**响应方式是「流式到某个上限,再封顶居中」**,不是「随视口无限拉伸」。

```
视口 375px(窄)          视口 900px(临界)        视口 2000px(宽)
┌───────────────┐        ┌───────────────────┐    ┌───────────────────────────────┐
│▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓│        │▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓│    │        ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓        │
│  内容撑满 100% │        │ 内容 = 视口 = 900  │    │  ←留白→  内容封顶900居中 ←留白→ │
└───────────────┘        └───────────────────┘    └───────────────────────────────┘
   流式(fluid)              刚好封顶                 封顶 + mx-auto 居中(两侧留白)
```

**为什么要封顶**:文本行太宽不可读。排版学的 measure(每行字符数)最佳区间约 45–75 字符;一行铺满
2000px 屏幕,眼睛从行尾跳回行首会跟丢。封顶是**为可读性服务**,不是偷懒。

## 2. 本仓的约定与实际取值

每个页面容器都是同一模板 `mx-auto max-w-[N] px-8 py-6`,只有 `N` 不同:

| 页面 | 文件 | max-width | 说明 |
|---|---|---|---|
| Token 趋势 | `web/src/pages/WorkTokensTrend.tsx:835` | **1760px** | 有大图表 + 多张构成卡,要宽 |
| 外部平台 | `web/src/pages/Providers.tsx:177` | **1100px** | 卡片列表 |
| 对话搜索 | `web/src/pages/AgentMessages.tsx:239` | **900px** | 搜索框 + 结果 + 图表 |

`N` 是**每页按内容量体裁衣**的值,不是全局常量。选错 `N` 才是 bug,不是「用了 max-width」。

## 3. `/agent-messages` 的错在哪(反面案例)

`AgentMessages.tsx:239` 用了 `max-w-[900px]`。它错的不是「写死宽度」,是三点叠加:

1. **照搬约定没量体裁衣**:顺手填了个比 Providers 更小的 900,没为这页调。
2. **值取太小 + 桌面独占**:项目 CLAUDE.md 明确「只面向 PC 宽屏、禁止横向滚动条」。宽屏上 900 居中
   = 内容只占不到一半、两侧各空数百 px,留白是封顶太窄的**副作用**,不是设计意图。
3. **一刀切套在需求相反的两块内容上**:同一个封顶同时罩住了
   - **图表**(recharts 窗口柱图)——它要**宽度**(同类的趋势页给了 1760),900 把柱子挤扁;
   - **搜索结果**(文本)——它要**窄 measure** 才好扫读。
   一个全局 `max-w` 无法同时满足「要宽的图」和「要窄的文本」。

## 4. 正确做法:分区自适应,而非一个全局封顶

对「桌面宽屏 + 混合内容(宽图 + 可读文本)」,正确的响应式不是「去掉封顶让全页流式」(那样文本行太长),
而是**按区域各给各的宽度策略**:

```
┌──────────────────────────────────────────────────────────┐
│ 页面外壳:宽(fluid 或大 max-width,如 1400/1760)          │
│  ┌────────────────────────────────────────────────────┐  │
│  │ 图表区:吃满外壳宽度(要宽)                          │  │
│  └────────────────────────────────────────────────────┘  │
│              ┌──────────────────────────┐                 │
│              │ 搜索框 + 结果:窄 measure  │  ← 内层再封顶   │
│              │ (如 max-w-[820px] 居中)  │     保可读       │
│              └──────────────────────────┘                 │
└──────────────────────────────────────────────────────────┘
```

即:**外壳放宽**(用满桌面横向空间)→ 图表区继承宽度 → 文本区**内层再套一个较窄的 `max-w`**
保 measure。封顶依然在用,只是**用在正确的层级**,一个页面可以有多个封顶,各服务各的内容。

## 5. 一句话原则

- `max-w + mx-auto` = 响应式的「流式到上限再封顶居中」,是可读内容列的标准手段,不是反响应式。
- 错误来自:**封顶取值不当**、或**用一个全局封顶去罩需求相反的多块内容**。
- 数据可视化(要宽)与正文(要 measure)并存时:**外壳放宽,文本内层再单独封顶**——分区自适应,
  而不是一刀切。
